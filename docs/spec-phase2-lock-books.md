# 画面ロックと複数帳簿（v0.41.0）

機能精査の E-1「画面ロック」と E-2「複数帳簿」。たかとの指示「提案してくれたものは全部実装して」（2026-10-29）による。
税法の判断は含まない。

## 画面ロック（E-1）

### 使い方

- その他 →「この端末」→「画面ロック」（`#/lock`）
- パスコード（数字4〜8桁）を2回入れて設定する。設定すると、次の場面で解除画面を出す
  - アプリを開いたとき（帳簿の画面を描く前にロックする）
  - ほかのアプリから戻ったとき（自動ロックまでの時間で決める）
  - 「今すぐロックする」を押したとき
- 自動ロックまでの時間：すぐ／1分／5分／15分（最初は「すぐ」）
  - 「すぐ」は裏に回った時点でロックする。iPhone のアプリ切替画面（スナップショット）にも帳簿を出さないため
  - 1分以上は、戻ったときに裏に回っていた時間を測って決める（`lock.js` の `needsLock`）
- Face ID・指紋など：端末が対応していれば（`isUserVerifyingPlatformAuthenticatorAvailable`）「Face ID・指紋などを登録する」を出す。登録すると解除画面に「Face ID・指紋などで解除する」が出る。パスコードでもいつでも解除できる
- パスコードの変更（今のパスコードが必要）、画面ロックをやめる（今のパスコードが必要）
- 解除画面の「パスコードを忘れたとき」：確認のうえ、この端末のすべての帳簿のデータと画面ロックを消して初期設定に戻す。バックアップファイルがあれば復元できる

### 仕組み（`js/lock.js`・`js/views/lock-screen.js`）

- 画面ロックは「端末を手にした人に帳簿を見られない」ためのもので、**データ（IndexedDB）は暗号化しない**。画面にもそう書いている
  - 暗号化しない理由：パスコードを忘れたときに復元できなくなる、全レコードの読み書きが重くなる、将来の同期の作りが複雑になる。必要になったら別に検討する
- パスコードはそのまま保存しない。PBKDF2（SHA-256、10万回、塩16バイト、出力256ビット）でハッシュにして保存し、照合は一定時間で比べる
- 続けて間違えたとき：4回までは待たない。5回目から30秒、以後2倍（最長15分）。回数と最後の時刻は端末の設定に保存するので、読み込み直しても待ち時間は続く。正しく解除したら0に戻す
- 解除画面はアプリの画面の上に重ねる（`body.is-locked` のとき、ほかの要素は `visibility: hidden`）。画面を作り直さないので、入力途中の仕訳や撮った証憑はロックの前後で残る
- Face ID など：WebAuthn（端末内の認証器 `platform`・本人確認 `required`・attestation なし）で登録した資格情報（credentialId）を覚え、解除のときにその資格情報で本人確認できたら解除する
  - サーバーが無いので**署名は検証しない**。確かめるのは、返ってきた資格情報の ID、`clientDataJSON` の種類（`webauthn.get`）・チャレンジ（毎回ランダムな32バイト）・オリジン
  - 署名を検証しても、検証する公開鍵が同じ端末の中にあるので、端末を操作できる人に対する強さは変わらない
- 保存先は端末のデータベース（下記）。バックアップファイルには入らず、復元しても画面ロックは変わらない

## 複数帳簿（E-2）

### 使い方

- その他 →「この端末」→「帳簿の切替」（`#/books`）
- 帳簿の一覧（作った順）。今開いている帳簿に「使用中」。ほかの帳簿は「この帳簿に切り替える」「削除」
- 「帳簿を追加する」：確認のうえ新しい帳簿に切り替え、初期設定（事業者名・個人/法人・会計期間）から始める
- 帳簿の名前は事業者名（設定を保存するたびに覚える）。初期設定前は「（初期設定がまだの帳簿）」
- 削除は確認のうえデータベースごと消す。今開いている帳簿は消せない
- 帳簿ごとに、事業者の設定・勘定科目・仕訳・固定資産・証憑・会計期間がすべて分かれる。バックアップ・CSV・決算書なども今の帳簿だけが対象
- 設定画面の「すべてのデータを消す」は今の帳簿だけを消す（ほかの帳簿と画面ロックは残る）

### 仕組み（`js/db.js` の `DeviceStore`）

- 帳簿ごとに IndexedDB のデータベースを分ける。帳簿の中身（ストア・スキーマ・`DB_VERSION`・移行・Repository）は今までと同じ
  - 1冊目は従来のデータベース名 `pocket-kaikei` のまま使う。今までのデータは移行なしで1冊目になる
  - 2冊目からは `pocket-kaikei-<帳簿のUUID>`
- 帳簿の一覧と画面ロックは、端末のデータベース `pocket-kaikei-device`（`DEVICE_DB_VERSION` 1）に置く
  - `books` ストア（keyPath `id`）：`{ id, dbName, label, createdAt, updatedAt }`
  - `kv` ストア（keyPath `key`）：`currentBookId`、`lock`（画面ロック。`id`・`createdAt`・`updatedAt` 付き）、`lockFailures`
  - 端末のデータベースは帳簿ではないので、バックアップにも将来の同期にも含めない。削除の記録（tombstones）も作らない
- 切り替えは読み込み直さずに行う（新しい帳簿のデータベースを開いてから古いほうを閉じる）。読み込み直すと画面ロックを聞き直すことになるため
- 帳簿の削除は、先にデータベースを消してから一覧から外す。ほかのタブで開いていて消せないときは一覧に残るので、やり直せる
- データベースの読み書きは、帳簿は Repository、端末の設定は `DeviceStore` だけが行う（画面から直接触らない）

## テスト（`test/lock-books.test.js`）と動作確認

- パスコードの形式・確認、ハッシュ（平文を含まない、塩ごとに違う、決まった塩なら同じ、256ビット）、照合、設定の検証
- 自動ロックの判定、続けて間違えたときの待ち時間
- WebAuthn の引数（platform・本人確認必須・ES256/RS256）と `clientDataJSON` の確認（種類・チャレンジ・オリジンが違えば不可）
- 帳簿：従来のデータベースが1冊目になる、追加・切替・名前・削除、帳簿ごとにデータが分かれる、今の帳簿は消せない
- 画面ロックの保存・間違えた回数・すべて消す
- Playwright（390×844、明暗）：`shots/lock-books/`。パスコードの設定（不一致のエラー）、仮想の認証器での Face ID 登録と解除、間違えたパスコード、読み込み直し後のロック（帳簿の画面を描かない）、5分設定で裏に回ったとき（すぐ戻ればロックしない、6分たてばロック）、帳簿の追加→法人のサンプル→個人の帳簿へ戻る（ロックを聞かない）→削除、画面ロックをやめる
